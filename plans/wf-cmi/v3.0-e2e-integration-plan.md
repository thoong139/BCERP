### 1.3 Lý do tích hợp (không phải tạo skill mới)

1. **Tránh trùng lặp** — wf-cmi Phase 2 đã build 6+7 graphs (entity/module/workflow/api/event/rbac + fe-component/fe-api-client/fe-permission/fe-route/be-domain/be-db-schema/be-cqrs). Đây là context DẦY HƠN nhiều so với input của wf-e2e-scenario hiện tại (chỉ có test-scenario.md skeleton từ F1).
2. **Loop-back giá trị cao** — failure root cause từ Phase 10 có thể tự append vào `gap-suggestions.json` Phase 7 → sidecar `business-invariants.json` → consume tự động ở lần chạy sau.
3. **Đơn giản hóa workflow** — user chạy 1 lệnh `/wf-cmi --exec-scenarios` thay vì sequence `/wf-cmi → /wf-e2e-finding → /wf-e2e-test → /wf-e2e-scenario`.
4. **Định hướng deprecate wf-e2e-*** — đã planned, không cần đầu tư bảo trì 12 skill.

### 3.2 Quy tắc routing mới

| Cờ kích hoạt | Profile | Hành vi |
|--------------|---------|---------|
| KHÔNG `--exec-scenarios` | bất kỳ | Pipeline dừng sau Phase 8. CD41 vẫn sinh scenario nếu profile=deep|exhaustive (artifact-only). |
| `--exec-scenarios` | quick / standard | Execute SUBSET — chỉ scenarios link MUST violation. AskUserQuestion confirm trước khi chạy. |
| `--exec-scenarios` | deep / exhaustive | Execute TOÀN BỘ scenarios CD41 sinh ra. Không hỏi (deep mặc định "verify mọi thứ"). |
| `--exec-scenarios --no-prompt` | bất kỳ | Bypass AskUserQuestion (cho CI). |
| `--scenarios-only` | bất kỳ | SKIP Phase 1-7, chỉ chạy Phase 9-10 trên scenarios session cũ. Yêu cầu `--session=<id>`. |

## 4. Chi tiết thiết kế

### 4.1 Lane mới CD41 — "E2E Scenario Synthesizer"

| Field | Value |
|-------|-------|
| Lane ID | `CD41` |
| Tên | E2E Scenario Synthesizer |
| Wave | **Wave 3** (final cross-ref) |
| Owner agents | `qa-lead` (primary) + `ux-researcher` + `business-analyst` |
| Profile activation | quick: SKIP / standard: SKIP / **deep: ACTIVE** / exhaustive: ACTIVE |
| Effort estimate | 3-5 ngày dev |
| Graph dependencies | workflow-graph (P2), api-graph (P2), fe-route-graph (P2), business-invariants (P3) |
| SSOT dependency | `ui-interactivity-spec.json` (CD38 SSOT — đã có v2.0) |
| Input | `signals-aggregated.jsonl` từ W1+W2, `business-invariants.json`, workflow-graph |
| Output | `phase4-coverage/lanes/CD41-e2e-synth/scenarios/test-scenario-CMI-{NN}-{slug}.md` × N, `scenarios-manifest.json`, `signals.json`, `lane-status.json`, `CD41-e2e-synth-report.md` |
| Concurrency budget | 1 (single writer per scenario file, parallel across scenarios với write isolation) |
| Time budget | 8-15 min cho 20-40 scenarios |

**Logic synthesis (rút gọn — chi tiết trong `procedures/lanes/CD41.md`):**

```
1. Filter violations: severity ∈ {MUST, HIGH} AND dim ∈ {CD9, CD11, CD13, CD15, CD23-26, CD38, CD39}
   (lanes có liên quan UX/cross-module/business flow)

2. Per violation, lookup:
   - invariant_id → business-invariants.json → expression + modules_involved
   - workflow-graph → find paths involving modules
   - api-graph → find endpoints touched
   - fe-route-graph → find routes user navigate

3. Render scenario template:
   - Tên: từ invariant_id + violation type (vd "Tạo Customer với SalesOwner inactive")
   - Loại: classify (Happy / Validation / Permission / BusinessRule)
   - Precondition: derive từ db-seed-data (nếu có) hoặc state machine
   - Actors: từ rbac-matrix
   - Bảng Bước:
     · Step 1: Navigate to entry URL (từ fe-route-graph)
     · Step 2-N: derive từ workflow-graph nodes
     · Last step: assertion theo invariant.expression

4. Cross-module flag: nếu violation.affected_modules length > 1 → mark cross_module=true
   → THÊM bước navigate xuyên modules theo workflow-graph

5. Write file: test-scenario-CMI-{NN}-{slug}.md theo template
6. Append manifest entry vào scenarios-manifest.json
7. Emit signal kind="E2E_SCENARIO_SYNTHESIZED" với count, cross_module_count, modules_covered
```

### 4.2 Phase 9 — E2E Execute & Verify

| Field | Value |
|-------|-------|
| Phase | 9 |
| Tên | E2E Execute & Verify |
| Mode | SEQUENTIAL (1 scenario tại 1 thời điểm, browser lock single) |
| Trigger | `--exec-scenarios` flag ON (BẮT BUỘC) |
| PRE-GATE | T1 scenarios-manifest exists / T2 Playwright MCP available / T3 FE running / T4 browser-mcp.lock acquirable |
| Output | `phase9-e2e-execute/{e2e-execution-report.md, e2e-results.json, screenshots/, lint-report.json, stable-registry.json, Phase9-report.md}` |
| Engine | Lazy-load `procedures/_e2e-runner.md` (port từ `scenario-runner.md`) |
| Auto-fix budget | 3 retries/scenario (browser fix only, source fix delegate sang Phase 10) |
| Time estimate | 30s-2min/scenario × N. 20 scenarios ≈ 10-40 min |

**Steps (chi tiết trong `procedures/phase9-e2e-execute.md`):**

```
Step 9.1  PRE-GATE T1-T4 + scenarios-manifest validation
Step 9.2  Acquire browser-mcp.lock (PID + ISO timestamp, TTL 30 min)
Step 9.3  Lint scenarios qua scripts/wf-cmi-e2e/lint-scenario.sh
          → fail → BLOCK execute, ghi lint-fixes.md, exit (E151)
Step 9.4  Pre-flight 5x stability check cho scenarios MỚI/MODIFIED
          (skip nếu hash đã có trong stable-registry với TTL 30 ngày)
          → 5/5 PASS → mark stable
          → 4/5 PASS → WARN continue
          → ≤3/5 PASS → auto-quarantine (E152), SKIP scenario
Step 9.5  Login qua Playwright MCP (nếu test có auth)
          → screenshot login-result.png
Step 9.6  FOR each scenario:
          a. Update e2e-results.json: current_scenario_idx, sub_state="executing"
          b. playwright_retry(navigate_to_entry_url, max=3)
          c. Execute steps from "Bước" column:
             · "Click ..." → browser_click
             · "Fill ... = ..." → browser_type
             · "Select ... from ..." → browser_select_option
             · "Wait ..." → browser_wait_for
             · "Navigate to ..." → browser_navigate
          d. After each step: browser_snapshot → verify "Kết quả mong đợi"
          e. Capture screenshot scenario-{NN}-{slug}.png
          f. Fill "Kết quả thực tế" + "Pass/Fail" vào test-scenario-CMI-{NN}.md
          g. IF FAIL → APPEND e2e-results.json issue entry, defer Phase 10
Step 9.7  Cross-module scenarios: navigate xuyên modules, verify FK consistency
Step 9.8  Release browser-mcp.lock
Step 9.9  Write e2e-execution-report.md (Tổng quan + Per scenario + Cross-module section)
Step 9.10 Update integrity-status.json: phases_completed += [9], current_phase = 10
Step 9.11 POST-GATE T1-T4
```

### 4.3 Phase 10 — E2E Resolution

| Field | Value |
|-------|-------|
| Phase | 10 |
| Tên | E2E Resolution |
| Mode | HYBRID (analysis sequential + spawn agents parallel max 3) |
| Trigger | Auto-run nếu Phase 9 có ≥1 FAIL. SKIP nếu Phase 9 0 FAIL. |
| PRE-GATE | T1 e2e-results.json có ≥1 FAIL entry / T2 failure-analyzer engine loadable / T3 agents available |
| Output | `phase10-e2e-resolution/{resolution-report.md, updated-gap-suggestions.json, Phase10-report.md}` |
| Engine | Lazy-load `procedures/_failure-analyzer.md` (port từ `failure-analyzer.md`) |
| Auto-fix budget | 3 retries/issue (browser fix + source fix tổng) |

**Steps (chi tiết trong `procedures/phase10-e2e-resolution.md`):**

```
Step 10.1 PRE-GATE check + load e2e-results.json FAIL entries
Step 10.2 FOR each FAIL issue:
          Bước 1 — Collect evidence:
            · CONSOLE = browser_console_messages
            · NETWORK = browser_network_requests
            · DOM = browser_snapshot
          Bước 2 — Classify failure_type (7 loại, priority):
            1. NETWORK_ERROR (4xx/5xx)
            2. AUTH_FAILURE (401/403)
            3. DATA_MISSING (404 or "không tìm thấy")
            4. TEST_SELECTOR ("Element not found")
            5. UI_BUG (TypeError/null in console)
            6. BUSINESS_RULE (catch-all)
            7. UNKNOWN
          Bước 3 — Xác định layer + owner:
            · NETWORK_ERROR → backend + developer
            · AUTH_FAILURE → backend + security
            · DATA_MISSING → database + dba
            · TEST_SELECTOR → test + qa-lead
            · UI_BUG → frontend + frontend-developer
            · BUSINESS_RULE → architecture + architect + domain-expert
            · UNKNOWN → manual triage
          Bước 4 — Resolution direction (template per type)
          Bước 5 — Enrich e2e-results.json entry
          Bước 6 — Accumulate vào resolution-report
          Bước 7 — Auto-Fix Attempt:
            Phase A (browser-fix, không touch source):
              · TEST_SELECTOR → thử 3 selector variant
              · AUTH_FAILURE → re-login
              · NETWORK 5xx → wait 3s retry
              · UI_BUG → page reload
              · DATA_MISSING → tạo data qua UI nếu có form
            Phase B (source-fix, spawn agent):
              · TEST_SELECTOR → qa-lead sửa selector trong scenario.md
              · AUTH_FAILURE → developer sửa RBAC middleware
              · NETWORK_ERROR → developer sửa endpoint/service
              · UI_BUG → frontend-developer sửa null check
              · BUSINESS_RULE → developer + domain expert
              · DATA_MISSING → dba tạo seed/migration
            Post-fix: wait HMR reload → re-run scenario → verify
            UNKNOWN → SKIP
Step 10.3 Loop-back vào Phase 7 gap-suggestions.json:
          FOR each issue có resolution:
            APPEND suggestion {
              kind: "e2e_scenario_fix",
              target_path: <file resolution sửa>,
              source_signal_ids: [issue.id],
              confidence: <0.5-0.95 tùy auto-fix kết quả>,
              severity: <inherit từ violation>,
              status: "proposed",
              rationale: <từ resolution-report>
            }
Step 10.4 Write resolution-report.md (Tổng quan + Per issue resolution + Spawn agent log)
Step 10.5 Update integrity-status.json
Step 10.6 POST-GATE T1-T4
```
