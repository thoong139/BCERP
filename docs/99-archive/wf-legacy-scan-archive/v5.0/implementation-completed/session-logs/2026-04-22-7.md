### F.3 — Incremental Mode

**New module:** `_shared/ips/incremental.py`

**Public API:**
```python
cs = inc.detect_changes(
    project_path, since_ref="HEAD~5",  # git mode
    previous_mtimes={...},              # or mtime fallback
    previous_content_hashes={...},      # optional for rename detect in mtime mode
)

plan = inc.classify_delta(cs)  # per-layer plan + auto-upgrade
next_state = inc.apply_delta(cs, previous_state)  # pure merge
```

**Thresholds (09-thresholds §2.3):**
- affected_pct > 25% → L4 full_reclassify (env: `LEGACY_SCAN_DELTA_RECLASSIFY_PCT`)
- affected_pct > 25% OR renames detected → L5 full_reextract
  (env: `LEGACY_SCAN_DELTA_REEXTRACT_PCT`)
- Rename detection rules (09 §2.3):
  * Exact content hash match, OR
  * Levenshtein distance ≤ 10% (v2.1 spec), OR
  * ≥ 3 matching function/class signatures

**detect_changes modes:**
- git_diff (when `since_ref` set + git repo): uses
  `git diff --name-status --find-renames=80 <ref> HEAD`.
- mtime (fallback): walks source files, compares against `previous_mtimes`.
  Rename detection in mtime mode requires `previous_content_hashes` —
  otherwise deleted + new stay separate (by design, documented).

## Design Decisions

### DD-F.1 — Impact graph builder is pure-function (no agents)

**Alternative:** spawn agent per module to classify relations.
**Rejected:** L3/L4/L5 already produce the inputs (dependency-graph,
classified modules, extracted features). L6 synthesis aggregates them.
Running agents again would duplicate work and break the L6 "main context,
no agents" invariant (02-scan-layers.md §4.6 attribute). impact_graph_builder
stays deterministic.

### DD-F.2 — Condensed mode skips edges entirely

**Alternative:** condensed keeps edges but limits to top-N.
**Rejected:** condensed target is ≤2,000 tokens total for project-context.md
(02-scan-layers.md §3). Any edges inflate downstream consumers'
token budget and contradict the mode purpose. Condensed keeps nodes (useful
for module map) but zero edges. Top-N would require sort-by-importance
heuristic that's out of scope for v5.0.

### DD-F.3 — Rename detection in mtime mode requires content hashes

**Alternative:** keep the deleted file's content in memory until after the
new file scan.
**Rejected:** detect_changes is called once with current state; by then the
deleted file is gone from disk. The cleanest contract is to accept optional
`previous_content_hashes` from the caller's persisted state (e.g.
previous_scan_state.json). Without it, mtime mode treats rename as
DELETE+ADD — documented as an intentional limitation. Git mode remains the
reliable path (git stores history).

### DD-F.4 — Auto-upgrade threshold at 25% (not 20%)

**Alternative:** 20% (original v2.0).
**Rejected:** v2.1 raised to 25% after wf-fix-bugs v6 R4 observation —
merging delta beyond 25% gets stuck in merge hell (affected scope > 1/4
total triggers exponential complexity). Env vars allow override for users
who want tighter incremental but default is 25%.

### DD-F.5 — Workload Gate does NOT touch registry / depth_map directly

**Alternative:** Gate downgrade directly writes
`scan-state.session.profile` and rebuilds depth_map.
**Rejected:** apply_user_choice returns an action dict only; the caller
(phase1-inventory.md Step 1.9c.3) is responsible for applying the change.
This keeps the module a pure policy engine and lets the orchestrator log
the transition properly (with before/after for audit).

## Scope Limitations

1. **impact-graph.json event_subscription + api_call cross-module defer v5.1.**
   These 2 relation types require runtime trace (not static analysis).
   `_build_edges_from_patterns` keeps heuristic signal detection but returns
   empty edges — documented inline. v5.1 will add runtime hook integration.

2. **Mtime rename detection is opt-in via content hashes.** If caller doesn't
   pass `previous_content_hashes` (which must come from a separate manifest
   persisted at previous scan), rename is treated as DELETE+ADD. Git mode
   remains the primary rename-detecting path.

3. **Workload Gate apply is orchestrator responsibility.** `workload_gate.py`
   only returns action dicts. Actual profile mutation + depth_map rebuild
   happens in `procedures/phase1-inventory.md` Step 1.9c.3 (tied to
   AskUserQuestion CDG) — not wired through Python. This matches the CDG
   contract (user confirmation is a Claude tool call, not a Python branch).

4. **`--cache-publish` + `--no-cache` CLI hook up.** Flags parsed + exported
   to state vars in F.4, but the actual `build_scan_cache(...,
   project_cache_enabled=CACHE_PUBLISH, no_cache=NO_CACHE)` call wiring
   happens in Phase H (Resume Routing) along with the other Phase E
   primitives. Phase F ships the input side; Phase H wires it into L2-L6
   spawn loops.

5. **Partition Planner deferred v5.1 (ADR-LS15 v2.1).** No fix-workload.json,
   no multi-session `--workload=<id> --chunk=<id>` handlers. Workload Gate
   only detects + offers 3 options. Verified by
   `test_no_fix_workload_json_generated`.
