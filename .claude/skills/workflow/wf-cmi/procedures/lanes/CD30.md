## §A Header

Lane CD30 đảm bảo **hai khía cạnh time + numbering** trong ERP logistics:

**(A) Time Integrity** — Mọi datetime nhất quán timezone-aware:
- DB: PostgreSQL `timestamptz` (KHÔNG `timestamp` naive)
- Domain: C# `DateTimeOffset` cho audit fields (KHÔNG `DateTime`)
- API: ISO-8601 + offset (vd `2026-05-16T10:30:00+07:00`)
- Storage: UTC chuẩn hóa, display: Asia/Ho_Chi_Minh (UTC+7) hoặc Asia/Shanghai (UTC+8)

**(B) Numbering Integrity** — Số chứng từ (Invoice, BOL, CustomsDeclaration, Quotation, Order):
- Duy nhất (UNIQUE constraint DB)
- Đúng format regex theo SSOT
- Đúng sequence rule (vd reset hàng năm/tháng)

**Vì sao logistics-critical (★★★):**
- Invoice VN theo TT 78/2021/TT-BTC: số duy nhất per năm tài chính + đúng prefix CQT
- Customs declaration VNACCS: mã do hệ thống VNACCS cấp — KHÔNG generate local
- Timezone drift = lệch giờ ETA tàu/máy bay (logistics-critical)
- Naive datetime → bug serve khách hàng nhiều múi giờ

### Step CD30.2 — Timezone-aware datetime check (NAIVE_DATETIME_STORAGE)

> Mọi business datetime column phải dùng `timestamptz` ở DB AND `DateTimeOffset` ở Domain.

**Logic:**
1. Iterate `be-db-schema-graph.json.columns[]` filter `sql_type IN ('timestamp', 'timestamp without time zone')` (naive):
   - Loại trừ columns trong SSOT `exclusions.legacy_naive_datetime[]` (grandfather)
   - Còn lại → NAIVE_DATETIME_STORAGE (severity MUST cho audit fields như CreatedAt/UpdatedAt/OccurredAt, severity SHOULD cho business datetime khác)
2. Iterate `be-domain-graph.json` properties filter `type == 'DateTime'` (không Offset):
   - Loại trừ properties tên matching pattern audit (CreatedAt/UpdatedAt) đã có MUST flag từ Step 1
   - Còn lại → NAIVE_DATETIME_STORAGE severity SHOULD

**Signal payload:**
```json
{
  "kind": "NAIVE_DATETIME_STORAGE",
  "severity": "MUST",
  "category": "VIOLATION",
  "rule_id": "TIME-CD30-001",
  "message": "Column Invoices.CreatedAt dùng timestamp (naive) — phải timestamptz để lưu UTC offset",
  "affected_columns": ["Invoices.CreatedAt"],
  "affected_files": ["apps/backend/Eureka.Modules.Finance/Migrations/20240101_InitialCreate.cs"],
  "evidence": [{"file": "...", "line": 45, "snippet": "CreatedAt = table.Column<DateTime>(type: \"timestamp\", ...)"}],
  "suggested_action": "Đổi sang timestamptz: column.HasColumnType(\"timestamp with time zone\") + entity property DateTimeOffset CreatedAt."
}
```

### Step CD30.3 — Timezone boundary drift (TIMEZONE_BOUNDARY_DRIFT)

> Cross-ref API → Domain → DB layers — phải nhất quán timezone semantics.

**Logic:**
1. Iterate `api-graph.json` endpoints có request/response field type=`date-time`:
   - Resolve endpoint → command/query trong `be-cqrs-graph.json` (matching handler)
   - Resolve command → entity property type trong `be-domain-graph.json`
   - Resolve entity → DB column type trong `be-db-schema-graph.json`
2. Check chain consistency:
   - API: ISO-8601 với offset → Domain: DateTimeOffset → DB: timestamptz ✅
   - API: ISO-8601 không offset → Domain: DateTime → DB: timestamp ❌ TIMEZONE_BOUNDARY_DRIFT (HIGH)
   - API: epoch number → Domain: DateTime → DB: bigint ❌ TIMEZONE_BOUNDARY_DRIFT (MUST — type mismatch)
3. Lệch giữa layers → TIMEZONE_BOUNDARY_DRIFT severity MUST

**Rule ID:** `TIME-CD30-002`

### Step CD30.4 — Numbering scheme uniqueness (MISSING_NUMBERING_UNIQUE)

> Mỗi document type declared trong `config.numbering_schemes[]` phải có UNIQUE constraint DB.

**Logic:**
1. Iterate `config.numbering_schemes[]` từ SSOT — mỗi entry: `{entity_name, column_name, format_regex, reset_policy, scope}` (vd Invoice prefix `INV-{YYYY}-{NNNNNN}` reset annually scope=tenant)
2. Cross-ref `be-db-schema-graph.json.indexes[]`:
   - Find index với `table=entity_name`, `unique=true`, `columns ⊇ [column_name]` (cộng `tenant_id` nếu scope=tenant, hoặc `year` nếu reset annually scope đến cấp year)
   - Không tìm thấy → MISSING_NUMBERING_UNIQUE (severity MUST — duplicate invoice number vi phạm thuế VN TT 78/2021)
3. Nếu UNIQUE chỉ có column_name mà scope=tenant → vẫn fail nếu thiếu composite (vd `[InvoiceNumber, TenantId]`)

**Rule ID:** `TIME-CD30-003`

### Step CD30.5 — Numbering format compliance (NUMBERING_FORMAT_VIOLATION)

> Sequence generator code phải tuân thủ format_regex declared trong SSOT.

**Logic:**
1. Iterate `numbering_schemes[].format_regex` (vd `^INV-\d{4}-\d{6}$`)
2. Grep code patterns (CI primary → Grep fallback):
   - `Grep "NumberGenerator|SequenceProvider|NextNumber|GenerateInvoiceNumber"` (case insensitive)
   - Extract format string từ code (vd `$"INV-{year}-{seq:D6}"` → regex `INV-\d{4}-\d{6}`)
3. Compare extracted format vs declared format_regex:
   - Mismatch → NUMBERING_FORMAT_VIOLATION (severity SHOULD)
   - vd code tạo `INV-{year}-{seq}` (không pad 6 digits) trong khi regex yêu cầu `\d{6}` → vi phạm

**Rule ID:** `TIME-CD30-004`

**Note:** Lane KHÔNG thực sự execute code — chỉ static analysis. Edge cases (dynamic format string) → log INFO suggestion để dev xác nhận thủ công.

### Step CD30.6 — Reset policy compliance (MISSING_NUMBERING_RESET)

> Nếu `reset_policy` declared (annually/monthly), code phải có logic reset.

**Logic:**
1. Iterate `numbering_schemes[]` filter `reset_policy IN ('annually', 'monthly', 'daily')`
2. Grep generator code:
   - Annually: phải có `WHERE EXTRACT(YEAR FROM CreatedAt) = {currentYear}` hoặc tương đương trong query MAX
   - Monthly: phải có `WHERE EXTRACT(YEAR_MONTH ...) = ...`
   - Daily: phải có `WHERE CreatedAt::date = CURRENT_DATE`
3. Không tìm thấy reset logic khi declared → MISSING_NUMBERING_RESET (severity MUST cho VN tax compliance — invoice năm sau bắt đầu từ 1)

**Rule ID:** `TIME-CD30-005`

### Step CD30.7 — Date-only vs datetime mismatch (DATE_TYPE_DRIFT)

> DB column `date` vs domain `DateOnly` (.NET 6+) phải đồng nhất.

**Logic:**
1. Iterate `be-db-schema-graph.json.columns[]` filter `sql_type = 'date'`:
   - Tìm entity property tương ứng trong `be-domain-graph.json` (match by table → entity → property name)
   - Nếu domain property type = `DateTime` (KHÔNG `DateOnly`) → DATE_TYPE_DRIFT (severity SHOULD — silent timezone bug khi cast date→datetime)
2. Iterate domain `DateOnly` properties:
   - Tìm DB column → nếu DB type ≠ `date` → DATE_TYPE_DRIFT (severity SHOULD)

**Rule ID:** `TIME-CD30-006`

**Exclusion:** Properties marked `[NotMapped]` hoặc shadow properties — log INFO không flag.

| Tier | Check | Tool | Fail action |

| T4 | `affected_columns[]` hoặc `affected_properties[]` mỗi signal resolve được trong graphs | jq | **E045** — Field unresolved → log WARN (không block) |

```bash
# T1
for f in signals.json CD30-time-numbering-integrity-report.md lane-status.json; do
  [ -f "$LANE_DIR/$f" ] || die "E044" "Output missing: $f"
done

# T2
SCHEMA=$(jq -r '."$schema"' "$LANE_DIR/signals.json")
LANE_VAL=$(jq -r '.lane' "$LANE_DIR/signals.json")
[ "$SCHEMA" = "signals-v1" ] || die "E044" "Schema mismatch: $SCHEMA"
[ "$LANE_VAL" = "CD30" ] || die "E044" "Lane field mismatch: $LANE_VAL"

FP_UNIQUE=$(jq '[.signals[].fingerprint] | unique | length' "$LANE_DIR/signals.json")
[ "$FP_TOTAL" = "$FP_UNIQUE" ] || die "E044" "Fingerprint collision: total=$FP_TOTAL unique=$FP_UNIQUE"

# T3
INVALID_RULES=$(jq -r --slurpfile ssot "$SSOT_WSM" \
  '[.signals[] | select(.rule_id | test("^TIME-CD30-[0-9]{3}$") | not) | .rule_id] | length' \
  "$LANE_DIR/signals.json")
[ "$INVALID_RULES" = "0" ] || die "E142" "Invalid rule_id format count: $INVALID_RULES"

ORPHAN_RULES=$(jq -r --slurpfile ssot "$SSOT_WSM" \
  '[.signals[].rule_id] - ($ssot[0].validation_rules // [] | map(.id)) | length' \
  "$LANE_DIR/signals.json")
[ "$ORPHAN_RULES" = "0" ] || log_warn "E142" "Orphan rule_id count: $ORPHAN_RULES"

# T4 — Field resolution (WARN only, không block)
UNRESOLVED=$(jq -r '[.signals[] | (.affected_columns // .affected_properties // [])[]] | length' \
  "$LANE_DIR/signals.json")
[ "$UNRESOLVED" -gt 0 ] && log_phase_event "phase4_cd30" "INFO" \
  "{\"affected_fields_count\":$UNRESOLVED}"
```
