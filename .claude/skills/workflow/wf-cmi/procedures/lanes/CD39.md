## §A Header

Lane CD39 đảm bảo **trải nghiệm lỗi nhân văn + có lối thoát** — phát hiện route thiếu error boundary, raw error.message render lên UI (security + UX risk), error code thiếu recovery action, message không phải tiếng Việt (vi phạm CORE-005), inconsistent display pattern. EUREKA-2026 dùng `Result<T>.Error` pattern + sonner/react-hot-toast + shadcn AlertDialog → CD39 critical để khách hàng VN không bị "Internal Server Error" thô bạo.

**Vì sao quan trọng (theo `error-code-catalog.json` validation_rules):**
- `MISSING_ERROR_BOUNDARY` (RULE-CD39-001, CRITICAL) → Route crash → toàn app blank screen
- `RAW_ERROR_LEAKED_TO_USER` (RULE-CD39-003, HIGH) → Lộ thông tin internal (stack trace, table names) → bảo mật risk + UX kém
- `MISSING_RECOVERY_ACTION` (RULE-CD39-004, HIGH) → User stuck, không biết phải làm gì tiếp
- `ERROR_MESSAGE_NOT_VIETNAMESE` (RULE-CD39-003, CRITICAL) → Vi phạm CORE-005 (Vietnamese docs/UI)
- `INCONSISTENT_ERROR_DISPLAY` (RULE-CD39-008, MEDIUM) → User confused giữa các pattern (modal vs toast vs inline)

### Step CD39.2 — Missing error boundary check (MISSING_ERROR_BOUNDARY)

> Next.js App Router: mỗi route segment (page hoặc layout) PHẢI có `error.tsx` cùng cấp HOẶC cấp cha (nested catch).

**Logic:**
1. Iterate `fe-route-graph.nodes[]` filter `kind="page"` HOẶC `kind="layout"`
2. Build set tất cả error boundaries: `ERROR_BOUNDARY_PATHS = jq '[.nodes[] | select(.kind == "error" or .kind == "not-found" or .kind == "global-error") | .route_path] | unique'`
3. Cho mỗi page node, check route_path có error boundary cùng cấp HOẶC cấp cha (path prefix)
4. Không có → MISSING_ERROR_BOUNDARY (severity HIGH cho page, MEDIUM cho nested layout)
5. Root layout (`/`) PHẢI có `global-error.tsx` — kiểm tra riêng (severity CRITICAL nếu thiếu)

**Signal payload:**
```json
{
  "kind": "MISSING_ERROR_BOUNDARY",
  "severity": "MUST",
  "category": "VIOLATION",
  "rule_id": "ERR-CD39-001",
  "ssot_rule_ref": "RULE-CD39-001",
  "message": "Route /crm/customer/[id]/edit không có error.tsx cùng cấp hoặc cấp cha — runtime error sẽ crash toàn nested tree",
  "affected_entities": ["/crm/customer/[id]/edit"],
  "affected_files": ["apps/erp-web/app/crm/customer/[id]/edit/page.tsx"],
  "evidence": [{"file": "apps/erp-web/app/crm/customer/[id]/edit/", "snippet": "Folder không có error.tsx; cấp cha /crm/customer/[id]/ cũng thiếu"}],
  "suggested_action": "Tạo apps/erp-web/app/crm/customer/[id]/error.tsx với fallback UI + retry button HOẶC tạo ở cấp cao hơn /crm/error.tsx"
}
```

### Step CD39.3 — Raw error leak detection (RAW_ERROR_LEAKED_TO_USER)

> Render `error.message` trực tiếp lên UI = lộ stack/internal info → bảo mật risk + UX kém.

**Logic:**
1. Grep code FE patterns nguy hiểm:
   - `toast(err.message)` / `toast(error.message)`
   - `<div>{error.message}</div>` / `<p>{err.message}</p>`
   - `alert(err.message)` (worse — blocking)
   - `console.error` rồi render output
2. Cross-ref với `fe-component-graph.nodes[]` để xác định component nào leak
3. Whitelist: file pattern `**/*.dev.tsx`, `**/_dev/**` (dev-only, không production)
4. → RAW_ERROR_LEAKED_TO_USER (severity HIGH)
5. Nếu SSOT available, cross-check error_codes catalog — nếu code có catalog entry → suggest replace với `t(err.code)` hoặc lookup catalog

**Rule ID:** `ERR-CD39-002` (maps SSOT `RULE-CD39-003 vi_message_required` + bảo mật concern)

**Bash example:**
```bash
RAW_LEAK_FILES=$(grep -rn -E "(toast|alert)\(\s*(err|error)\.message" apps/erp-web/ --include="*.tsx" --include="*.ts" \
  | grep -vE "(\.dev\.tsx|/_dev/)" || true)
```

### Step CD39.4 — Missing recovery action coverage (MISSING_RECOVERY_ACTION)

> Mỗi error code trong catalog có `recovery_action` declared nhưng UI KHÔNG render action button (retry/go-back/contact-support).

**Logic:**
1. Iterate `SSOT_ERROR_CODES[]` filter `recovery_action != null` AND `recovery_action != "none"`
2. Cho mỗi error code, build expected UI component pattern:
   - `recovery_action="retry"` → expect `<RetryButton>` hoặc `onClick={refetch}`
   - `recovery_action="contact_support"` → expect link/button `<ContactSupportLink>`
   - `recovery_action="go_back"` → expect `router.back()` hoặc `<BackButton>`
   - `recovery_action="login_redirect"` → expect `signIn()` call
3. Grep code FE cho component patterns
4. Không có → MISSING_RECOVERY_ACTION (severity HIGH)
5. Cross-ref `recovery_actions[]` catalog (nếu có) để build mapping chi tiết

**Rule ID:** `ERR-CD39-003` (maps SSOT `RULE-CD39-004 recovery_action_declared`)

**Note:** Nếu SSOT_AVAILABLE=0, skip step này (fallback heuristic không đủ context). Log INFO "skipped — SSOT required".

### Step CD39.5 — Vietnamese message check (ERROR_MESSAGE_NOT_VIETNAMESE)

> CORE-005 (Vietnamese docs/UI): mỗi error code phải có `display_messages.vi` populated.

**Logic:**
1. Iterate `SSOT_ERROR_CODES[]`
2. Check field `display_messages.vi` — nếu null/empty → ERROR_MESSAGE_NOT_VIETNAMESE (CRITICAL — vi phạm CORE-005)
3. Nếu fallback `display_messages.en` được dùng làm primary → severity CRITICAL
4. Nếu render raw error code (vd `ERR_INVALID_CUSTOMER`) lên UI → severity CRITICAL
5. Cross-ref FE code: grep i18n keys `t('errors.XXX')` — verify mọi error code có i18n entry

**Rule ID:** `ERR-CD39-004` (maps SSOT `RULE-CD39-003 vi_message_required`)

**EUREKA-specific:** Customer-facing UI 100% tiếng Việt (logistics VN), staff UI có thể bilingual VN+EN. Nếu detect i18n locale = "vi-VN" mà message en → CRITICAL.

### Step CD39.6 — Consistent display pattern check (INCONSISTENT_ERROR_DISPLAY)

> Mỗi severity có UI pattern declared (vd CRITICAL=modal+block, HIGH=toast-red, MEDIUM=inline-warn).

**Logic:**
1. Iterate `SSOT_UI_PATTERNS[]` (nếu có) cho mapping severity → component pattern
2. Cross-ref FE code: detect component dùng cho mỗi error code
   - sonner `toast.error()` → toast pattern
   - shadcn `<AlertDialog>` → modal pattern
   - inline `<Alert variant="destructive">` → inline pattern
3. Compare actual pattern vs SSOT declared pattern cho severity:
   - CRITICAL error nhưng dùng toast (không block user) → INCONSISTENT_ERROR_DISPLAY (severity MEDIUM)
   - MEDIUM error dùng modal (over-engineer block user) → INCONSISTENT_ERROR_DISPLAY (severity LOW/MAY)
4. Build heatmap: severity vs actual pattern

**Rule ID:** `ERR-CD39-005` (maps SSOT `RULE-CD39-008 i18n_keys_present` extended scope)

**Note:** Severity MEDIUM (không hard-block) — đây là UX consistency, không phải bug functional.

    "scan_duration_sec": ($scan_duration | tonumber),
    "signals": $signals,
    "metadata": {

      "severity_breakdown": {
        "MUST": ([$signals[] | select(.severity == "MUST")] | length),
        "SHOULD": ([$signals[] | select(.severity == "SHOULD")] | length),
        "MAY": ([$signals[] | select(.severity == "MAY")] | length),
        "INFO": ([$signals[] | select(.severity == "INFO")] | length)
      },
      "category_breakdown": {
        "MISSING_INVARIANT": ([$signals[] | select(.category == "MISSING_INVARIANT")] | length),
        "VIOLATION": ([$signals[] | select(.category == "VIOLATION")] | length),
        "GAP": ([$signals[] | select(.category == "GAP")] | length),
        "RECOMMENDATION": ([$signals[] | select(.category == "RECOMMENDATION")] | length)

      "modules_covered": $modules_covered,
      "ssot_source": "error-code-catalog.json",
      "ssot_available": ($ssot_avail == 1),
      "ci_source": $ci,
      "fallback_used": ($ssot_avail == 0)

## §D POST-GATE (T1→T4 + Auto-Fix)

| Tier | Check | Tool | Fail action |
|------|-------|------|-------------|
| T1 | 3 output files exist | bash | **E044** — Output missing → auto-fix retry x3 |
| T2 | `signals.json` schema = `signals-v1`, `lane` = "CD39", fingerprint unique | jq | **E044** — Schema invalid → re-build |
| T3 | Mọi signal `rule_id` match format `ERR-CD39-\d{3}` (001-005) | jq | **E045** — Format invalid → re-render |
| T4 | Mọi `ssot_rule_ref` (nếu SSOT loaded) resolve trong `validation_rules.rules[].id` | jq | **E045** — SSOT ref unresolved → log WARN |

```bash
# T1
for f in signals.json CD39-error-ux-recovery-report.md lane-status.json; do
  [ -f "$LANE_DIR/$f" ] || die "E044" "Output missing: $f"
done

# T2
SCHEMA=$(jq -r '."$schema"' "$LANE_DIR/signals.json")
LANE_VAL=$(jq -r '.lane' "$LANE_DIR/signals.json")
[ "$SCHEMA" = "signals-v1" ] || die "E044" "Schema mismatch"
[ "$LANE_VAL" = "CD39" ] || die "E044" "Lane field mismatch"

FP_TOTAL=$(jq '.signals | length' "$LANE_DIR/signals.json")
FP_UNIQUE=$(jq '[.signals[].fingerprint] | unique | length' "$LANE_DIR/signals.json")
[ "$FP_TOTAL" = "$FP_UNIQUE" ] || die "E044" "Fingerprint collision"

# T3
INVALID_RULES=$(jq -r '[.signals[] | select(.rule_id | test("^ERR-CD39-[0-9]{3}$") | not) | .rule_id] | length' "$LANE_DIR/signals.json")
[ "$INVALID_RULES" = "0" ] || die "E045" "Invalid rule_id format: $INVALID_RULES"

# T4 — SSOT ref resolution (WARN only, chỉ check nếu SSOT_AVAILABLE)
if [ "$SSOT_AVAILABLE" = "1" ]; then
  UNRESOLVED_REF=$(jq -r --slurpfile ssot "$SSOT_ERR" \
    '[.signals[] | .ssot_rule_ref // empty] | unique
     | map(select(. as $r | ($ssot[0].validation_rules.rules | map(.id) | index($r)) == null))
     | length' "$LANE_DIR/signals.json")
  [ "$UNRESOLVED_REF" = "0" ] || log_warn "E045" "Unresolved SSOT refs: $UNRESOLVED_REF"
fi
```

**Auto-fix budget (CORE-034):** Max 3 retries. Hết → ESCALATE FAIL.
