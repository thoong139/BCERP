## C1.10.1 — Cross-Module Pattern Comparison Engine: WARN

**Kiểm tra:** QD11 prompt có tự động phát hiện và so sánh entity forms, list/table views, workflow steps, action buttons giữa 2+ module cùng domain không?

### Positive Findings

1. **Pass 1 prompt covers all 4 areas explicitly:**
   - §1.1 Entity Form Comparison: fields, types, validators
   - §1.2 List/Table Feature Comparison: search, filter, sort, pagination, export
   - §1.3 Action Button Comparison: Save/Cancel/Reset/Delete/Export/Import/Duplicate/Archive/Send
   - §1.4 Workflow Step Comparison: approval, notifications, status transitions

2. **Domain-aware filtering:** §3 of the prompt explicitly instructs NOT to compare modules from different domains (có counter-example §5.3: CRM vs HR = KHÔNG compare).

3. **Cross-module dependency resolution:** `qd11-workflow.md` Phase 1 Step 3 loads `cross_module_dependencies[]` from `req-registry.json` to determine module pairs.

4. **Skip conditions properly enforced:**
   - `single_module` → skip (E111, `wf-fix-qd11-skip-check.sh`)
   - `api_only` → skip (E112)
   - `profile_quick` → skip (E113)
   - E116: No `cross_module_dependencies` → skip Pass 1, continue Pass 2+3

5. **ISG recommender wiring:** `isg_recommender.py` line 127 maps shared/common/utils paths → QD11 (weak weight 0.9), line 129 maps registry/dependency config changes → QD11 (weak).

6. **Lane dispatch wiring:** `lane_dispatch.py` line 354-357 defines `P-QD11-llm-business-completeness` probe with `dimensions=("QD11",)`.

### Gap

**Reliance on `cross_module_dependencies[]` without fallback auto-detection:**
The engine depends entirely on `cross_module_dependencies[]` from `req-registry.json` to identify which modules to compare. If this array is missing or empty, Pass 1 is skipped (E116). There is no fallback mechanism to auto-detect modules from the same domain by grouping on `registry.departments[]` or `module.domain` field. This means if the registry was populated by a skill that doesn't fill `cross_module_dependencies[]`, the cross-module comparison won't run even when same-domain modules exist.

**Evidence:** `qd11-workflow.md` line 3: "Xác định module pairs cho cross-module comparison (cùng domain)" — but implementation relies solely on `cross_module_dependencies[]` from registry.

**Severity:** LOW — E116 handles the missing case gracefully (skip Pass 1, continue Pass 2+3). QD11 still produces value from Pass 2 and Pass 3 even without cross-module comparison.

### Verdict: WARN

Engine design is sound with all 4 comparison areas covered. The single point of failure is the dependency on `cross_module_dependencies[]` — no auto-detection fallback for same-domain module grouping.

## C1.10.2 — Form Field Completeness Detection: PASS

**Kiểm tra:** Có phát hiện MISSING_FIELD, TYPE_MISMATCH, VALIDATION_GAP khi form thiếu field so với module tham chiếu không?

### Findings

1. **MISSING_FIELD:** Prompt §1.1.1 — "Field ton tai trong reference module nhung thieu trong target module." Example: CRM có "tax_code" trong customer form nhưng Procurement không có "tax_code" trong supplier form. Severity: MEDIUM. CDG-ENHANCEMENT flag.

2. **TYPE_MISMATCH:** Prompt §1.1.2 — "Cung field name nhung khac type giua cac module." Example: "amount" là DECIMAL(10,2) trong Sales nhưng INTEGER trong Invoice. Severity: MEDIUM. Bump to HIGH if causes silent data loss when sharing data.

3. **VALIDATION_GAP:** Prompt §1.1.3 — "Reference module co validation (required, format, range) nhung target module khong co." Example: Sales validates phone format but CRM doesn't. Severity: LOW. Bump to MEDIUM if compliance validation.

4. **Severity calibration correct:** dimension.json §severity_rules maps MEDIUM → MISSING_FIELD, TYPE_MISMATCH; LOW → VALIDATION_GAP. SKILL.md §Severity Rules matches.

5. **Counter-examples for false positives:** §5.3 shows CRM vs HR example where industry field difference should NOT be emitted (different domains).

6. **Evidence structure in signals:** §5.1 shows proper signal structure with `target_module`, `reference_module`, `detail`, `suggestion`, `evidence.code_snippet`, `evidence.confidence`.

7. **Eval coverage:** TC-QD11-001 tests MISSING_FIELD signal emission for cross-module form comparison (CRM + Sales modules, CustomerForm missing tax_id).

### Verdict: PASS

All three signal types (MISSING_FIELD, TYPE_MISMATCH, VALIDATION_GAP) are explicitly covered with detection criteria, severity calibration, positive examples, and counter-examples. Eval TC-QD11-001 validates the path.

**Kiểm tra:** Có phát hiện thiếu Save/Cancel/Delete/Export/Approve/Reject dựa trên cross-module comparison không?

### Findings

1. **Form action buttons covered in §1.3:**
   - Save/Submit → §1.3 action comparison covers "Save/Cancel/Reset/Delete"
   - Cancel → explicitly covered
   - Delete → explicitly covered
   - Export → explicitly covered
   - Import → explicitly covered

2. **Workflow action buttons split to §1.4:**
   - Approve → covered in §1.4 "approval flow (submit → review → approve)"
   - Reject → implicitly covered in §1.4 "approval flow"
   - BUT: "Approve" and "Reject" are not explicitly named in §1.3 or §1.4

3. **Pattern-based principle enforced:** Prompt §3 states "Features chi co 1 module co: Khong co reference module de so sanh → KHONG emit" — preventing fantasy suggestions.

4. **SKILL.md §Action Button Sufficiency** (audit checklist reference) lists: Save/Submit, Cancel/Back, Reset, Edit, Delete, Back to List, Export/Print, Add New, Export, Import, Batch Action, Approve, Reject, Request Change, Delegate. The prompt §1.3 covers a subset of these.

5. **Gap:** The prompt's §1.3 is action button comparison as a single bullet point (line 30: "7. MISSING_FEATURE (action): Reference module co 'Duplicate' / 'Archive' / 'Send Email' action, target module thieu."). Compared to forms (§1.1 with 3 sub-points) and lists (§1.2 with 3 sub-points), action buttons are treated as a single catch-all category.

### Verdict: WARN

The action button section (§1.3) is thin — one bullet point vs 3 sub-points for forms and lists. Approve/Reject are never explicitly named as button types in the prompt. The LLM may miss workflow-action buttons if it only focuses on §1.3 for button analysis. Severity: LOW — LLM is inherently capable of inferring workflow buttons from §1.4 context, and the pattern-based principle prevents false positives.

   - **Search:** §1.2.4 — "Module A co search full-text + filter theo status/date, module B cung domain chi co sort don gian" ✓
   - **Column filter:** §1.2.4 — "filter theo status/date" (filter theo cột, implied) ✓
   - **Sort:** §1.2.4 — "sort don gian" ✓

The LLM could potentially detect this through general pattern inference, but without explicit instruction, the detection rate for column visibility gaps will be lower than for other table features. Severity: LOW — column visibility is a nice-to-have UX feature, not a core business completeness concern.

## C1.10.5 — Workflow Step Completeness: WARN

**Kiểm tra:** Có phát hiện thiếu approval step, notification trigger, status transition, audit log so với module tham chiếu không?

### Findings

1. **Approval step:** §1.4 — "Reference module co approval flow (submit → review → approve) nhung target module cung loai chi co direct save" ✓ (explicit example)

2. **Status transition:** §1.4 — "submit → review → approve" ✓ (explicit example)

3. **Notification trigger:** §1.4 header mentions "notifications" in the description text: "So sanh approval steps, notifications, status transitions" but there is NO detailed detection example or explicit MISSING_FEATURE subtype for missing notification triggers. The single signal example in §1.4 is "MISSING_FEATURE (workflow)" which bundles approval + notification + status as one signal type.

4. **Audit log:** NOT in Pass 1 (§1.4). Audit log detection is in Pass 2 (domain heuristic — MISSING_AUDIT_TRAIL, `llm-probe-qd11-domain-heuristic.md` §1.3). This means:
   - Standard profile: no audit log detection (Pass 2 only runs deep+)
   - Deep/exhaustive profile: audit log detected via domain heuristic, not cross-module comparison

5. **Section is thin:** §1.4 is the least detailed section in the prompt:
   - §1.1 (Forms): 3 sub-points with explicit signal types + examples
   - §1.2 (Lists): 3 sub-points
   - §1.3 (Buttons): 1 sub-point
   - §1.4 (Workflows): 1 sub-point, no sub-categorization
   
   The entire workflow detection logic is: "Reference module co approval flow (submit → review → approve) nhung target module cung loai chi co direct save" — which only covers single-step vs multi-step workflow comparison.

6. **Missing workflow patterns:** The prompt doesn't explicitly instruct to detect:
   - Parallel approval (multiple approvers at same step)
   - Conditional approval routing (if amount > X → director, else → manager)
   - Escalation paths (timeout → auto-escalate)
   - Rejection with reason (reject → back to submitter with comments)
   - Notification triggers per step (who gets notified when)

### Verdict: WARN

The workflow step comparison section is the weakest of the 4 cross-module comparison areas. Only 2 lines of detection logic compared to 6-8 lines for other sections. Notification triggers are mentioned in the header but not elaborated with detection patterns or examples. Audit log detection is relegated to Pass 2 (domain heuristic) which only runs on deep+ profile. Complex workflow patterns (parallel approval, conditional routing, escalation) are not covered at all. Severity: MEDIUM — workflow completeness is a core business concern; thin coverage here limits QD11's ability to detect missing workflow steps.
