## C1.10.6 — Domain-Specific Field Requirements

### Evaluation: WARN

**What was checked:**
- Pass 2 (`llm-probe-qd11-domain-heuristic.md`) §1.1 lists mandatory fields for 11 domains
- §1.2 covers compliance & regulatory checks (HIPAA, SOX, PCI-DSS, FERPA, COSO ERM 2017, ISO 31000)
- §1.3 covers audit trail requirements (Finance, Healthcare, Legal, HR)
- §1.4 covers domain-specific business rules (IFRS 15, HS code, 3-bid rule)
- §3 guard: "Domain rules KHONG duoc de cap trong `.claude/references/team-expert/` → KHONG emit. Khong tu nghi ra domain rule."

**Findings:**

1. **Domain coverage is comprehensive.** All 11 domains from the audit checklist (E-commerce/Retail, HR, Finance, Logistics, Healthcare) + 6 more (Insurance, Real Estate, Manufacturing, Procurement, Legal, Education) have mandatory fields listed. Severity calibration table maps each signal type to default severity + bump conditions.

2. **WARN: References non-existent `domain-rules.md`.** The prompt's positive example (5.1, line 105) references `.claude/references/team-expert/healthcare/domain-rules.md §2.1`. However, `domain-rules.md` does NOT exist in any domain reference directory. The actual files are `controls.md`, `operations.md`, `compliance.md`, `personas.md`, etc. This creates a reference path that the LLM would fail to resolve at runtime, potentially causing the probe to (a) emit with weak evidence or (b) skip legitimate findings because it can't find the referenced file.

   ```bash
   # Evidence — no domain-rules.md exists
   $ glob "**/domain-rules.md" in .claude/references/team-expert/
   → No files found
   ```

3. **Counter-example 5.3 is well-constructed.** It shows a case where the LLM should NOT emit (small warehouse doesn't need ISO 9001), teaching scale-appropriate judgment. This reduces false positive risk.

4. **Domain reference structure varies by domain.** Some domains (healthcare) have `compliance.md` with regulatory frameworks, while others (finance, hr) have `operations.md` with process frameworks but no dedicated regulatory compliance file. The prompt doesn't provide guidance on which reference files to look for per domain — relies on LLM to discover.

5. **OBS-038:** Prompt example also references `.claude/references/team-expert/manufacturing/` with a rule about ">50 employees" threshold for QMS — but manufacturing domain references (personas.md, processes.md, controls.md) don't contain this employee-count threshold explicitly. The example may be illustrating a fictional rule that doesn't exist in the references, which could train the LLM to invent thresholds.

**DoD:** WARN — domain coverage is broad and well-structured, but the `domain-rules.md` reference path doesn't resolve and counter-example thresholds may not exist in source files.

## C1.10.7 — Cross-Module Consistency Enforcement

### Evaluation: WARN

**What was checked:**
- Pass 1 (`llm-probe-qd11-cross-module.md`) signal types vs audit checklist's 4 inconsistency categories
- Pass 2 and Pass 3 for overlap coverage

**Coverage matrix:**

| Audit Category | Covered? | QD11 Signal Type | Location |
|---------------|----------|-----------------|----------|
| NAMING_INCONSISTENCY | **NO** | — | Not in any prompt |
| TYPE_INCONSISTENCY | **YES** | TYPE_MISMATCH | Pass 1 §1.1.2 |
| MESSAGE_INCONSISTENCY | **NO** | — | Not in any prompt |
| ENUM_INCONSISTENCY | **NO** | — | Not in any prompt |

**Details:**

1. **TYPE_INCONSISTENCY → TYPE_MISMATCH (covered).** Pass 1 §1.1.2 explicitly detects "Cung field name nhung khac type giua cac module" with the example of `discount` being DECIMAL(5,2) in Sales but INTEGER in Invoice. Example 5.2 demonstrates this fully with evidence, suggestion, and remediation.

2. **NAMING_INCONSISTENCY → NOT covered.** Pass 1 §3.1 says "Differences ve naming convention: kebab-case vs camelCase vs snake_case — KHONG emit." This is about code style conventions, NOT about semantic naming inconsistencies. The audit wants detection of same entity with different field names across modules (e.g., `customer.tax_code` in CRM vs `customer.tax_id` in Sales). The prompt's DO-NOT-EMIT rule for naming conventions may cause the LLM to also miss legitimate NAMING_INCONSISTENCY signals.

3. **MESSAGE_INCONSISTENCY → NOT covered.** No probe checks whether the same validation rule produces different error messages across modules (e.g., "Phone không hợp lệ" in CRM vs "Số điện thoại sai định dạng" in Sales). The prompt only checks for presence/absence of validation (VALIDATION_GAP), not message consistency.

4. **ENUM_INCONSISTENCY → NOT covered.** No probe compares enum values for the same status flow across modules (e.g., OrderStatus has `{PENDING, CONFIRMED, SHIPPED}` in Module A but `{NEW, PROCESSING, DONE}` in Module B). The prompt checks for MISSING_FEATURE (workflow) but not enum value consistency.

5. **OBS-039:** The 4 audit categories (NAMING, TYPE, MESSAGE, ENUM inconsistency) are not mentioned as explicit signal types in any QD11 prompt. They appear only in the audit checklist, suggesting a specification gap: the audit checklist expects detection of patterns that the prompts weren't designed to detect.

**DoD:** WARN — TYPE_INCONSISTENCY is covered via TYPE_MISMATCH, but 3/4 inconsistency categories (NAMING, MESSAGE, ENUM) have zero coverage across all 3 QD11 passes. This is a significant gap for cross-module consistency enforcement.

## C1.10.8 — Enhancement Suggestion Quality Control

### Evaluation: WARN

**What was checked:**
- Required fields per suggestion: evidence, rationale, severity, confidence
- Quality gate mechanism (≥80% must have evidence)
- Fantasy reporting risk

**Findings:**

1. **Evidence field is present in all examples.** Pass 1 examples (5.1, 5.2) include `evidence.code_snippet` + `evidence.confidence` + `evidence.ci_citation`. Pass 2 examples (5.1, 5.2) include `evidence.code_snippet` + `evidence.confidence`. Pass 3 examples (5.1, 5.2) include `evidence.code_snippet` + `evidence.confidence`. The evidence structure is consistent across all 3 passes.

2. **Rationale is embedded in `description`, not a separate field.** The audit checklist says each suggestion needs "rationale: lý do đề xuất (1-2 câu, tiếng Việt)." All prompt examples use `description` for this purpose (e.g., "Trong Sales module (reference), nguoi dung co the export danh sach don hang ra PDF... Ca 2 module cung domain (finance/sales), cung nguoi dung ke toan — ho can export invoice de gui cho khach hang."). The description field serves as rationale but is not formally labeled as such. This is acceptable in practice — the description IS the rationale.

3. **Severity calibration is mostly correct.** Pass 1: MISSING_FEATURE=HIGH, MISSING_FIELD=MEDIUM, TYPE_MISMATCH=MEDIUM, VALIDATION_GAP=LOW — aligns with the audit's expected levels. Pass 2: MISSING_COMPLIANCE_CHECK=HIGH, MISSING_BUSINESS_RULE=HIGH, MISSING_DOMAIN_FIELD=MEDIUM, MISSING_AUDIT_TRAIL=MEDIUM — correct. Pass 3: UNIMPLEMENTED_REQ=HIGH, ORPHAN_REQ_ID=MEDIUM, GAP_REQ_TO_FEAT=MEDIUM — correct. The severity tables all have bump conditions that can escalate severity appropriately.

4. **Confidence scores are included.** Pass 1 examples show confidence 0.85 (HIGH). Pass 2 examples show confidence 0.75 (MEDIUM). Pass 3 examples show confidence 0.95 (HIGHEST). The SKILL.md labels pass confidences as HIGH/MEDIUM/HIGHEST, which matches.

5. **WARN: No structural quality gate for ≥80% evidence rate.** The audit checklist states ">20% suggestions thiếu evidence → FAIL." None of the prompts, procedures, or dimension.json contain a gate that checks the evidence rate across all suggestions. There is no post-processing step that counts suggestions-with-evidence vs suggestions-without-evidence and fails if >20% are missing evidence. The signal validation (qd11-workflow.md Phase 3) only does schema validation + dedup, not evidence-rate quality control.

6. **Counter-examples reduce fantasy reporting risk.** Each prompt has a "KHONG focus" section with explicit counter-examples. Pass 1 has 5 no-emit rules. Pass 2 has 4 no-emit rules. Pass 3 has 5 no-emit rules. These are well-crafted and domain-specific. However, counter-examples are qualitative guardrails — they don't replace a structural gate.

7. **OBS-040:** `fixability` field varies across prompt examples. Pass 1.5.1 has `fixability: "agent_fix"`. Pass 1.5.2 has `fixability: "manual_fix"`. Pass 2.5.1 has `fixability: "agent_fix"`. Pass 2.5.2 has `fixability: "manual_fix"`. Pass 3.5.1 has `fixability: "agent_fix"`. Pass 3.5.2 has `fixability: "manual_fix"`. But there's no specification of when to use which fixability level — relies on LLM judgment.

**DoD:** WARN — signal examples are high quality with evidence, confidence, severity, and rationale, but there is no structural quality gate to enforce the "≤20% suggestions without evidence" requirement. This is a procedural gap, not a prompt gap.

## C1.10.9 — CDG Gate Enhancement Review

### Evaluation: WARN

**What was checked:**
- CDG gate flow for HIGH/MEDIUM/LOW signals
- CDG token recording
- Anti-auto-implement guard
- Conflict between SKILL.md and qd11-cdg-gate.md

**Findings:**

1. **HIGH/CRITICAL CDG gate is correctly defined.** qd11-cdg-gate.md Step 1: CDG triggered when `severity ∈ {HIGH, CRITICAL}`. Step 3: Per-signal ACCEPT/REJECT/DEFER with user prompt. SKILL.md: "KHÔNG auto-implement enhancement suggestions — day la BUSINESS decision, khong phai ky thuat." This is correct.

2. **CDG tokens are properly recorded.** qd11-cdg-gate.md Step 5 writes decisions to `$SESSION_DIR/cdg-tokens.json` with atomic write (`.tmp.$$` + `mv`). The token structure includes per-signal decision, reason, and timestamp.

3. **Anti-loop guard is present.** Max 2 CDG cycles for QD11, with E113 for 2 consecutive rejects → force accept + warning. `cdg_reject_counts.qd11` tracked in fix-status.json.

4. **WARN: MEDIUM signal CDG policy CONFLICT between SKILL.md and qd11-cdg-gate.md.**

   | Source | MEDIUM Policy |
   |--------|--------------|
   | SKILL.md §Fix Rules | "CDG gate — user ACCEPT/REJECT hoac auto-accept" |
   | SKILL.md §POST-GATE §CDG Gate | "Moi HIGH/MEDIUM enhancement suggestion duoc trinh bay cho user qua CDG gate" |
   | qd11-cdg-gate.md Step 1 | "MEDIUM/LOW signals được auto-accept (không cần CDG)" |
   | qd11-cdg-gate.md POST-GATE | "MEDIUM/LOW signals: auto-accept (không cần CDG)" |
   | Audit checklist C1.10.9 | MEDIUM → "summary, user có thể ACCEPT ALL / REJECT ALL / REVIEW" |

   **The qd11-cdg-gate.md procedure (authoritative for runtime) auto-accepts MEDIUM signals without CDG, while SKILL.md (user-facing) says MEDIUM goes through CDG. The audit checklist expects MEDIUM to show a summary with batch ACCEPT/REJECT/REVIEW.**

5. **LOW signals: auto-accept.** Both SKILL.md and qd11-cdg-gate.md agree. Correct per audit checklist.

6. **dimension.json `cdg` flag doesn't match severity-based CDG logic.** dimension.json sets `cdg: true` only for P-QD11-cross-module-comparison probe, and `cdg: false` for P-QD11-domain-heuristic and P-QD11-registry-gap. However, the CDG gate is severity-based (HIGH/CRITICAL), not probe-based. A MISSING_BUSINESS_RULE (HIGH) from Pass 2 would NOT trigger CDG per dimension.json (cdg=false), but WOULD trigger CDG per severity-based logic in qd11-cdg-gate.md.

7. **OBS-041:** The qd11-cdg-gate.md procedure has no "ACCEPT ALL / REJECT ALL / REVIEW" batch mode for MEDIUM signals. The audit checklist expects batch operations for MEDIUM severity, but the procedure only defines per-signal ACCEPT/REJECT/DEFER (for HIGH/CRITICAL). This means even if MEDIUM were routed to CDG, there's no efficient batch UI.

**DoD:** WARN — HIGH/CRITICAL CDG gate is well-defined with anti-loop, tokens, and error codes. MEDIUM signal CDG policy is contradictory between SKILL.md (CDG with summary) and qd11-cdg-gate.md (auto-accept). dimension.json's per-probe `cdg` flag conflicts with the severity-based CDG logic in procedures.

## C1.10.10 — Skip & Applicability Conditions

### Evaluation: PASS

**What was checked:**
- Skip conditions and their correctness
- Skip reason logging
- Scope eligibility (when QD11 SHOULD run)

**Findings:**

1. **3 explicit skip conditions, correctly defined:**

   | Condition | Source | Reason | Verification |
   |-----------|--------|--------|-------------|
   | `single_module` | dimension.json:173, SKILL.md:44, qd11-workflow.md:9 | "khong the cross-reference giua cac module cung domain" | Error E111 logs `lane-status.skipped, reason=single_module` |
   | `api_only` | dimension.json:174, SKILL.md:45, qd11-workflow.md:9 | "khong co UI de so sanh entity forms/lists" | Error E112 logs `lane-status.skipped, reason=api_only` |
   | `profile_quick` | dimension.json:175, SKILL.md:46, qd11-workflow.md:9 | "LLM-heavy completeness analysis" | Error E113 logs `lane-status.skipped, reason=profile_quick` |

2. **Skip reason is always logged.** All 3 conditions → STOP → ghi `lane-status.json` with `status=skipped` + `reason=<skip_reason>`. Không "skip âm thầm."

3. **Graceful sub-pass skips defined.** Beyond the 3 hard skips, there are 3 soft skips for individual passes:
   - E116: No `cross_module_dependencies[]` → skip Pass 1 only, continue Pass 2+3
   - E117: No domain references → skip Pass 2 only, continue Pass 1+3
   - E118: No registry → skip Pass 3 only, continue Pass 1+2

4. **Skip check uses dedicated bash script.** qd11-workflow.md Step PRE-GATE.2 references `bash .claude/scripts/wf-fix-qd11-skip-check.sh --project-root <root> --profile <profile>`. This provides consistent, testable skip logic.

5. **Scope eligibility: implicit from skip negation.** The audit checklist says "Không skip: 2+ modules cùng domain, có UI, profile ≥ standard." This maps to: NOT single_module AND NOT api_only AND NOT profile_quick. The logic is implicit (if no skip condition triggers, QD11 runs) rather than explicit (positive eligibility check). However, the implicit approach is correct and simpler — no false eligibility gate to maintain.

6. **WARN (minor): No explicit "same domain" check.** The skip conditions check module count ≥ 2 but don't verify the modules are in the SAME domain. If a project has 2 modules in completely different domains (e.g., HR + Logistics), QD11 would run but Pass 1 cross-module comparison would be meaningless (the prompt §3.4 says "Differences do domain khac nhau → KHONG emit"). The cost is wasted LLM tokens, not false positives. This is handled gracefully by the prompt's DO-NOT-EMIT rule.

7. **OBS-042:** E116 (no cross_module_dependencies) skips Pass 1 but SKILL.md §Prerequisites says `req-registry.json co >=2 modules cung domain (cross_module_dependencies[])`. The prerequisite is stated as a hard requirement, but the error handling treats it as a soft requirement (skip Pass 1 only). This is a minor inconsistency: prerequisite vs error handling disagree on severity.

**DoD:** PASS — skip conditions match audit requirements exactly. Skip always logs reason. Graceful sub-pass degradation is well-designed. Minor: no explicit same-domain eligibility check (but prompt guardrails handle this); E116 soft-skip conflicts with prerequisite language.
