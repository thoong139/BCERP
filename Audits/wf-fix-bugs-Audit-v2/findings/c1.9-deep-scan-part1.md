## C1.9.1 — UI Component Discovery Exhaustiveness

**Verdict:** WARN

### Evidence

**Files audited:**
- `.claude/skills/workflow/wf-fix-bugs/prompts/llm-probe-qd5-ux-a11y.md` — 18 UX/a11y pattern categories, NO component-type enumeration
- `.claude/skills/workflow/wf-fix-bugs/prompts/llm-probe-qd9-runtime-health.md` — 23 runtime patterns, NO component-type enumeration
- `.claude/skills/workflow/wf-fix-functional/procedures/probes/P-QD1-deep-ui-traversal.md` — Extracts buttons, forms, inputs, nav links from page snapshot (partial)
- `.claude/skills/workflow/wf-fix-ux-a11y/procedures/probes/P-QD5-ui-traversal-deep.md` — Link-based traversal, no component enumeration
- `.claude/skills/workflow/wf-fix-runtime-health/procedures/probes/P-QD9-interactive-smoke.md` — Finds ALL buttons (4 selector types), max 10/route

### Analysis

**What works:**
1. **QD1 deep UI traversal** (B1, `:42-47`): Parses page snapshot and extracts `$BUTTONS[]`, `$FORMS[]`, `$INPUTS[]` — covers 3 component types explicitly.
2. **QD9 interactive-smoke** (A2, `:218-222`): Discovers buttons via 4 selectors (`button`, `[role=button]`, `.btn`, `input[type=submit/button]`) — systematic button discovery.
3. **QD5 UI traversal**: Discovers all same-origin links from homepage — covers navigation components.
4. **Static probes** (grep-based): Scan ALL source files — inherently find all components in code.

**What's missing:**
1. **No pre-scan component-type catalog**: The system doesn't run `grep -rnE '<(button|input|select|textarea|form|dialog|modal|popup|sheet|drawer|menu|dropdown|combobox|tabs|accordion|toast|tooltip|carousel)' src/` before starting probes.
2. **LLM probes are pattern-focused, not component-focused**: QD5 prompt (§1.1-1.2) lists 18 *patterns* (loading states, error states, etc.) but never says "enumerate all component instances." The LLM discovers components implicitly when they match a pattern.
3. **Missing component types in explicit discovery**: `select`, `textarea`, `dialog`, `modal`, `popup`, `sheet`, `drawer`, `menu`, `dropdown`, `combobox`, `tabs`, `accordion`, `toast`, `tooltip`, `carousel` — none of these are explicitly enumerated in any probe's discovery phase.
4. **QD5 LLM probe** §1.2 mentions modal/focus-trap (#14) and aria-live (#12) but these are behavior checks, not discovery instructions.

### Rationale for WARN (not FAIL)

Static probes (grep across all files) + page-level runtime traversal provide decent coverage of visible components. The system finds most components through these mechanisms. However, the lack of explicit component-type enumeration means some component types may be under-analyzed (e.g., carousel, combobox, accordion have no dedicated probe logic). Rating WARN because coverage is estimated 90-95% not guaranteed 100%.

## C1.9.2 — Nested Component Drill-Down

**Verdict:** WARN

### Evidence

**Files audited:**
- `.claude/skills/workflow/wf-fix-bugs/prompts/llm-probe-qd5-ux-a11y.md` §1.2 #11, #14 — Focus management + modal escape (behavior checks, not drill-down)
- `.claude/skills/workflow/wf-fix-ux-a11y/procedures/probes/P-QD5-ui-traversal-deep.md` — Link traversal only, no modal-content recursion
- `.claude/skills/workflow/wf-fix-runtime-health/procedures/probes/P-QD9-interactive-smoke.md` A2 `:232-332` — Clicks buttons, captures post-click DOM
- `.claude/skills/workflow/wf-fix-functional/procedures/probes/P-QD1-deep-ui-traversal.md` A2 `:125-151` — Clicks primary CTAs, checks response (modal/dialog appearance)

### Analysis

**What works:**
1. **Static probes**: Scan all files recursively → inherently find components nested at any depth.
2. **QD1 A2** (`:138-142`): After clicking CTA, checks "Modal/dialog xuất hiện?" → detects modal opened by button click.
3. **QD9 interactive-smoke** (A2.5 `:274-278`): After clicking button, captures `AFTER_SNAPSHOT` and checks `MODAL_COUNT` → detects modals in post-click DOM.
4. **QD5 deep traversal** (exhaustive profile, `:116-131`): Clicks up to 5 buttons per page, waits 500ms → post-click snapshot may capture modal content.

**What's missing:**
1. **No recursive drill-down instruction**: If button-click opens modal → modal contains form → form has "Advanced" button → opens nested dialog. The second dialog's components would never be tested because:
   - QD9 interactive-smoke scans CTAs BEFORE clicking, not AFTER
   - After clicking a CTA, the probe navigates BACK to the original page (`:310-315`) rather than drilling into the newly-opened modal
2. **Post-modal-open CTA re-scan missing**: QD9 interactive-smoke discovers buttons from the initial page snapshot. If a modal opens and contains NEW buttons (Save, Cancel, Next), those buttons are NOT in the initial CTA list and won't be tested.
3. **QD1 A2** (`:125-151`): Tests "primary CTAs" (text-matched: Submit, Save, Create, etc.). CTAs inside modals may not match these text patterns and would be skipped.
4. **No explicit "popup→form→table→dialog" chain traversal** in any probe. The probes navigate linearly (visit page → interact → go back) rather than recursively (visit page → open modal → interact with modal contents → drill deeper).

### Rationale for WARN (not FAIL)

Static probes cover nested components at source level. Runtime probes DO detect modals opened by button clicks. However, they don't recursively drill into modal contents to test nested components. A modal with a form containing a "Configure" button that opens a third-level dialog would have its innermost components untested at runtime. Rating WARN because deep nesting (>2 levels) is uncommon in practice, so real-world coverage remains good.

## C1.9.3 — Feature Boundary Completeness

**Verdict:** WARN

### Evidence

**Files audited:**
- `.claude/skills/workflow/wf-fix-runtime-health/procedures/probes/P-QD9-feature-checklist-smoke.md` — Feature-level smoke from registry
- `.claude/skills/workflow/wf-fix-bugs/prompts/llm-probe-qd1-functional.md` — Functional pattern detection
- `.claude/skills/workflow/wf-fix-bugs/prompts/llm-probe-qd2-business.md` — Business rule detection
- `.claude/skills/workflow/wf-fix-bugs/prompts/llm-probe-qd5-ux-a11y.md` — UX state patterns

### Analysis

**What works:**
1. **P-QD9-feature-checklist-smoke** (S1, `:86-117`): Reads registry for features with `impl_status=done`, builds checklist with routes, navigates each, checks CTA + state change. This is the closest thing to feature-boundary scanning.
2. **QD1 LLM probe** (§1.1-1.2): 14 functional bug categories that apply to ALL features — edge cases, null deref, race conditions, etc.
3. **QD5 LLM probe** (§1.1-1.2): 18 UX/a11y patterns covering loading/error/empty states — these apply per-feature.
4. **Static probes**: REQ-ID xref, calculation checks — verify feature implementation against requirements.

**What's missing:**
1. **No sub-flow enumeration per feature**: The checklist requirement specifies each feature should be verified for: list screen, add flow, edit flow, delete flow, empty state, loading state, error state. None of the probes systematically enumerate these sub-flows.
2. **Feature completeness depends on registry quality**: P-QD9-feature-checklist-smoke only finds features that have `impl_status=done` AND have `ui_routes[]` or `route` fields in registry. Features without route info in registry are skipped.
3. **Pattern-based, not feature-based**: The system finds bugs by pattern (e.g., "missing loading state anywhere") rather than by feature ("for User Management feature, verify add flow has loading state"). This means a feature could have 4/5 sub-flows covered, miss 1, and no probe would flag "feature incomplete."
4. **No feature flow diagram construction**: The checklist suggests drawing a flow diagram per feature, then comparing scan results. No probe does this.

### Rationale for WARN (not FAIL)

The combination of registry-based feature discovery + pattern-based probes provides decent feature coverage. The QD9 feature-checklist-smoke specifically navigates each feature route and checks CTA behavior. However, the lack of systematic sub-flow enumeration means the system can't guarantee "every sub-flow of every feature was verified." This is a structural gap, not a coverage gap — the probes would find bugs IN sub-flows that exist, but they can't detect MISSING sub-flow verification.

## C1.9.4 — Dynamic/Conditional Content Discovery

**Verdict:** WARN

### Evidence

**Files audited:**
- `.claude/skills/workflow/wf-fix-bugs/prompts/llm-probe-qd5-ux-a11y.md` §1.2 #12 — aria-live for dynamic content
- `.claude/skills/workflow/wf-fix-bugs/prompts/llm-probe-qd9-runtime-health.md` §1.3 #10 — Dynamic import fail without fallback; §1.5 #18 — Conditional field logic
- `.claude/skills/workflow/wf-fix-runtime-health/procedures/probes/P-QD9-spa-route-coverage.md` — Router config extraction, finds ALL routes including lazy-loaded
- `.claude/skills/workflow/wf-fix-runtime-health/procedures/probes/P-QD9-interactive-smoke.md` — Button clicks that may reveal conditional content

### Analysis

**What works:**
1. **Static probes**: grep-based probes scan ALL source files → inherently cover conditional renders (`v-if`, `{condition &&}`, `hidden`, `display:none`).
2. **P-QD9-spa-route-coverage**: Extracts ALL routes from router config (Next.js pages/, React Router createBrowserRouter, Vue Router) — includes lazy-loaded routes that wouldn't be found by link traversal alone.
3. **QD9 LLM probe** §1.3 #10: Explicitly checks for `React.lazy()` without `<Suspense fallback>` — covers lazy-loaded component errors.
4. **QD9 LLM probe** §1.5 #18: Explicitly checks conditional field logic — "If payment method = bank-transfer, show bank fields" toggle logic.
5. **QD5 LLM probe** §1.2 #12: `aria-live` missing for dynamic content — covers dynamic content announcements.

**What's missing:**
1. **No explicit conditional-render enumeration**: No probe runs `grep -rnE '(v-if|ngIf|\{.*&&|hidden|display:\s*none|visibility:\s*hidden)' src/` to catalog all conditional content locations, then verify each.
2. **Auth-gated content discovery gap**: Runtime probes navigate with available auth context (AUTH_SESSION if present). Content gated behind roles/permissions the session doesn't have won't be tested. The LLM probes can find the code but can't verify runtime behavior.
3. **Tab/accordion hidden content**: Content inside inactive tabs/accordion panels is in the DOM (for client-side tabs) or not (for server-rendered tabs). No probe explicitly clicks tabs/accordions to reveal hidden content.
4. **Content rendered after API response**: QD9 LLM probe §1.2 #6 covers network error handling, but no probe systematically tracks "this component renders after fetch()" and checks what happens when the API is slow/errors.

### Rationale for WARN (not FAIL)

Static probes provide inherent coverage of conditional code (they grep all files). SPA route coverage ensures lazy-loaded routes are discovered. The main gaps are auth-gated content (requires specific auth context) and tab-hidden content (requires explicit tab interaction). These are hard problems that even dedicated E2E test suites struggle with. Rating WARN because the system acknowledges these limitations (P-QD9-feature-checklist-smoke skips auth-walled routes with a note, doesn't silently miss them).

## C1.9.5 — Interactive Element State Coverage

**Verdict:** WARN

### Evidence

**Files audited:**
- `.claude/skills/workflow/wf-fix-bugs/prompts/llm-probe-qd5-ux-a11y.md` §1.1, §2 — Loading/error/empty states + severity calibration
- `.claude/skills/workflow/wf-fix-bugs/prompts/llm-probe-qd9-runtime-health.md` §1.4-1.5 — CTA disabled, form validation, form dirty state
- `.claude/skills/workflow/wf-fix-runtime-health/procedures/probes/P-QD9-interactive-smoke.md` — CTA click + state change detection
- `.claude/skills/workflow/wf-fix-ux-a11y/procedures/probes/P-QD5-ui-traversal-deep.md` — Page-level error detection

### Analysis

**Checklist requirement vs actual coverage:**

| Element Type | Required States | Covered? | Gap |
|---|---|---|---|
| **Button** | enabled, disabled, loading, clicked | Partial | Clicked tested (QD1 A2, QD9 interactive-smoke). Disabled checked (QD9 LLM #13). Loading NOT systematically tested at runtime. |
| **Form field** | empty, filled, invalid, disabled, readonly | Partial | Empty/filled tested implicitly. Invalid checked (QD5 #5, #13). Disabled/readonly NOT tested. |
| **Form** | submitting, validation error, submit success, submit error | Partial | Submitting NOT tested. Validation error checked (QD5 #5). Submit success checked (QD1 A3). Submit error checked (QD5 #2). |
| **Popup/Sheet/Dialog** | opening, open (idle), submitting, closing, closed | Partial | Opening/open detected (QD1 A2). Closing checked (QD5 #14 modal escape). Submitting NOT tested. Closed NOT tested. |
| **Table/List** | empty, loading, populated, error, paginating | Partial | Empty checked (QD5 #3). Loading checked (QD5 #1). Error checked (QD5 #2). Populated tested implicitly. Paginating NOT tested. |
| **Dropdown/Combobox** | closed, open, searching, selected, no results | Missing | NOT covered by any probe. Neither QD5 nor QD9 LLM prompts mention dropdown/combobox states. |

**What works:**
1. **Loading/error/empty states**: QD5 LLM probe explicitly covers these 3 states across all component types.
2. **Button clicked state**: QD1 A2 + QD9 interactive-smoke systematically click buttons and verify response.
3. **Modal open/close**: QD5 #14 checks modal escape/focus trap. QD1 A2 detects modal after click.

**What's missing:**
1. **No systematic per-element-type state enumeration**: The probes check individual patterns (e.g., "missing loading state") rather than "for each button, verify all states."
2. **Dropdown/combobox state coverage completely absent**: No probe checks dropdown open/close, search within dropdown, selection behavior, or "no results" state.
3. **Button disabled/loading states**: QD9 LLM #13 checks if CTA is disabled during loading, but this is a specific pattern check, not systematic. No runtime probe programmatically verifies button disabled attribute.
4. **Table paginating state**: No probe paginates through table pages. C1.9.8 (part of next task) specifically covers this.
5. **Form field disabled/readonly**: Not explicitly covered by any probe.

### Rationale for WARN (not FAIL)

The system covers the most important states (loading, error, empty, clicked) through pattern-based probes. However, the lack of systematic per-element-type state verification means some state gaps (dropdown states, paginating, form field disabled/readonly) exist. These are genuine coverage gaps but affect non-critical states. Rating WARN because the core states for the most common elements are covered.

## Observations

### OBS-020: Component-type enumeration is implicit, not explicit
The system relies on page traversal + pattern matching to discover components. A pre-scan phase that catalogs all component types in source (via grep) and cross-references with probe coverage would provide explicit coverage guarantees.

### OBS-021: Recursive drill-down is depth-1 only
Runtime probes detect modals opened by button clicks but don't re-scan modal contents for nested interactive elements. This means deeply nested component chains (modal→form→tabs→button-in-tab-3) are only covered by static probes.

### OBS-022: Feature sub-flow completeness depends on registry quality
P-QD9-feature-checklist-smoke is the only feature-level scan but requires features to have UI routes in the registry. Features without route metadata are skipped silently.

### OBS-023: Dropdown/combobox is a blind spot
Neither QD5 nor QD9 LLM prompts, nor any runtime probe, explicitly covers dropdown/combobox behavior (open/close/search/select/no-results). This is a complete coverage gap for a common UI pattern.

### OBS-024: Auth-gated content discovery is honest about limitations
P-QD9-feature-checklist-smoke (Fallback Table, `:528`) explicitly handles auth-walled routes (401/403) by skipping with a note rather than emitting false errors. This is correct behavior but means auth-gated features are not verified at runtime.

---

## Recommendations

1. **C1.9.1**: Add a pre-scan phase that greps for all component types and emits a component catalog. Cross-reference with probe output to verify coverage.
2. **C1.9.2**: For deep/exhaustive profiles, add recursive drill-down: when a modal/dialog is detected, re-run CTA discovery on the modal contents before closing it.
3. **C1.9.3**: Add a sub-flow template per feature type (CRUD, dashboard, workflow) that probes can use to verify completeness.
4. **C1.9.4**: Add explicit grep for conditional render patterns as a pre-scan check. For auth-gated content, document the limitation and suggest manual verification.
5. **C1.9.5**: Add dropdown/combobox state probe (P-QD5-dropdown-state-check or P-QD9-dropdown-smoke). Extend interactive-smoke to verify button disabled attribute.
