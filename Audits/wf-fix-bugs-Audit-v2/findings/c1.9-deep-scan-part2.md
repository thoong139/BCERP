## C1.9.6 — Cross-Component State Flow Detection

### What the checklist requires

> Skill phát hiện và kiểm tra: Popup submit → parent list refresh → item mới xuất hiện; Delete confirm → item biến mất khỏi list; Filter thay đổi → table reload; Tab switch → nội dung tab mới load; Form field thay đổi → field khác update (cascading).

### What the probes actually do

**Runtime probes (QD1, QD9):** All three runtime probes (`P-QD1-deep-ui-traversal` A2, `P-QD9-interactive-smoke` A2.5/A2.6, `P-QD9-feature-checklist-smoke` A3 Step 4-5) use the same fundamental detection mechanism:

```
Click CTA → wait 2s → compare: DOM length before/after, URL before/after, modal count
```

This is a **generic state change detector** — it answers "did clicking this button change anything on the page?" It does NOT answer "did the action on component A cause the expected change on component B?"

**Specific gaps vs checklist requirements:**

| Required cross-component flow | Coverage status |
|------------------------------|-----------------|
| Popup submit → parent list refresh → new item appears | **NOT COVERED** — probes check if popup submit changes DOM/URL, NOT whether the parent list behind the popup refreshed |
| Delete confirm → item disappears from list | **NOT COVERED** — delete buttons are in the "destructive skip list" (`delete|remove|destroy`). Probes explicitly skip clicking them (BHV-002). |
| Filter change → table reload | **NOT COVERED** — no probe interacts with filter controls and then verifies table content changed |
| Tab switch → content loads in adjacent panel | **NOT COVERED** — no probe explicitly clicks tabs and verifies tab panel content changed |
| Form field change → cascading field update | **NOT COVERED** — QD1 A3 tests form submission (fill all → submit), not cascading field interactions |

**QD10 LLM probe (`llm-probe-qd10-integration.md`):** This probe covers cross-module integration at the architectural/code level:
- Event emitter/listener mismatch detection (§1.3)
- Cross-module state machine violations (§1.6)
- Business flow violations (§1.6.20)

This is valuable but operates at the **static code analysis** level, not the **runtime UI interaction** level the checklist demands. It analyzes import graphs and event wiring, not browser-based cross-component state flow.

**Evidence:**
- `P-QD9-interactive-smoke.md:274-278` — A2.5 captures DOM_LEN_AFTER, URL_AFTER, AFTER_SNAPSHOT, MODAL_COUNT
- `P-QD9-interactive-smoke.md:280-283` — A2.6 comparison: `DOM_CHANGED`, `URL_CHANGED` booleans
- `P-QD9-interactive-smoke.md:284` — Signal emit condition: all three unchanged → emit `ui_cta_no_response`
- `P-QD9-interactive-smoke.md:135-138` — Destructive skip list includes `delete|remove|destroy`
- `P-QD1-deep-ui-traversal.md:125-151` — A2 "Test primary CTAs": same click → wait → compare pattern

### Verdict: WARN

Cross-component state flow detection exists at the generic level (any state change) and at the architectural level (QD10 LLM), but NOT at the specific UI interaction level the checklist requires (component A action → component B specific change). The destructive skip list prevents testing delete→list-refresh flows entirely.

## C1.9.7 — Module/System Boundary Coverage

### What the checklist requires

> So sánh file tree của scope với danh sách files được scan. Xác minh 100% files trong scope được scan. Mọi route/endpoint trong scope được probe.

### What the probes actually do

**Scope determination** is session-level (`--scope=all|system|module`, `--name`, `--since`), not per-probe file enumeration:

- `SKILL.md:78-80` — Scope args: `all`, `system`, `module` with `--name` for narrow scope
- `phase1-engine.md:139-181` — Step 3.5 incremental scope restriction via `git diff --name-only <ref> HEAD` → maps files to modules → sets `SCOPE_MODULES`

**File discovery in probes** is route-based and registry-based, not file-tree-based:

1. **Homepage link traversal** (`P-QD9-interactive-smoke` B1/B2, `P-QD1-deep-ui-traversal` B1/B2): Parse `<a href>` from homepage snapshot → build NAV_ROUTES queue. MAX_ROUTES=20/50/100 per profile.
2. **Registry lookup** (`P-QD9-feature-checklist-smoke` S1): `jq '.requirements[] | select(.impl_status=="done")'` → features with routes.
3. **Navigation specs** (`P-QD9-feature-checklist-smoke` S2): Parse `.mc-data/docs/phase4-ux/Navigation-*.md` → extract route paths.
4. **Feature specs** (`P-QD9-feature-checklist-smoke` S3): Parse `.mc-data/docs/phase2-features/*.md` → extract route hints.
5. **Code grep for routes** (`P-QD5-ui-traversal-deep` B1): `grep -rnE '(path:|href=|to=|navigate\()["\x27]/' src/` → static route extraction.
6. **CI augmentation** (GitNexus `query("navigation, route, link")`): Augment route list with SPA routes.

**What's missing:**

| Mechanism | Exists? |
|-----------|---------|
| Enumerate all files in scope | **NO** — scope is module/conceptual, not file-list-based |
| Enumerate all routes in source code | **PARTIAL** — QD5 B1 greps routes from code, but limited to 50 lines |
| Cross-reference file tree with scan results | **NO** — no step compares "what should be scanned" with "what was scanned" |
| Verify 100% files in scope probed | **NO** — no post-scan boundary verification |
| Skip reason tracking for unscanned files | **NO** — probes track their own skips (e.g., "no_cta_found"), not scope-level omissions |
| LLM probe file scoping | **PARTIAL** — `phase1-engine.md:557` uses `scope.file_globs` + `scope.max_files` for LLM invocations, but this is an input filter, not a post-scan verification |

**Evidence:**
- `phase1-engine.md:557` — `Glob source files theo scope.file_globs từ scope.source_dir, limit scope.max_files` (input scoping only)
- `P-QD9-interactive-smoke.md:87-101` — B1/B2: link-based route discovery, no file-tree comparison
- `P-QD9-feature-checklist-smoke.md:81-117` — S1/S2/S3: registry + spec-based feature discovery, no file enumeration
- `P-QD5-ui-traversal-deep.md:33-37` — B1: grep for routes in code, `head -50`, static only

### Verdict: WARN

Scope boundary coverage is implicit — probes discover what to scan through routes, registry, and specs, but there is no explicit mechanism to enumerate all files in scope and verify every one was probed. No post-scan file-tree-to-results cross-reference exists.

## C1.9.8 — Pagination & Infinite Scroll Exhaustiveness

### What the checklist requires

> Với mọi table/list có pagination hoặc infinite scroll: test page 1, page 2, page cuối, "không có dữ liệu"; page size change; sort + pagination; filter + pagination. Infinite scroll: test scroll → load more, scroll → hết dữ liệu.

### What the probes actually do

**Runtime probes treat each route as a single page.** No probe has pagination-specific interaction logic:

| Probe | Pagination handling |
|-------|-------------------|
| `P-QD1-deep-ui-traversal` | A1 traverses NAV_ROUTES up to MAX_PAGES=20. Each route is one page. No pagination control interaction. |
| `P-QD9-interactive-smoke` | A2 clicks CTAs per route. MAX_ROUTES=20/50. No pagination-specific logic. |
| `P-QD9-feature-checklist-smoke` | A3 navigates feature routes from registry. Checks page load + CTA response. No pagination interaction. |
| `P-QD5-ui-traversal-deep` | B2 Playwright crawl: visits links, collects console errors. No pagination interaction. |

**LLM probes touch pagination tangentially:**

| Probe | Coverage |
|-------|----------|
| `llm-probe-qd10-integration.md` (§1.2.8) | "Pagination contract drift" — detects when backend changes `{items, total}` → `{data, meta: {total}}`. API-level, not UI-level. |
| `llm-probe-qd4-performance.md` (§8) | "API over-fetching: missing pagination" — detects missing pagination as performance issue. |
| `llm-probe-qd4-performance.md` (§13) | "Infinite scroll memory bloat" — detects unbounded list render without virtualization. |

**Specific gaps:**

| Required pagination test | Coverage |
|--------------------------|----------|
| Test page 1 of paginated table | **INCIDENTAL** — if the route is in NAV_LINKS, page 1 is visited |
| Test page 2 | **NOT COVERED** — no probe clicks "next page" or navigates to `?page=2` |
| Test last page | **NOT COVERED** — no logic to determine and navigate to last page |
| Test "no data" state | **NOT COVERED** — no logic to navigate past the last page |
| Page size change (10→25→50) | **NOT COVERED** — no probe interacts with page-size selector |
| Sort click → list reordered | **NOT COVERED** — no probe clicks column headers |
| Filter + pagination combined | **NOT COVERED** — no filter interaction at all |
| Infinite scroll: load more | **NOT COVERED** — no scroll simulation |
| Infinite scroll: end of data | **NOT COVERED** — no scroll-to-exhaustion logic |

**Evidence:**
- `P-QD1-deep-ui-traversal.md:97-123` — A1: traversal loop visits each route once, no within-page pagination
- `P-QD9-interactive-smoke.md:183-332` — A2: per-route CTA loop, clicks buttons, compares state, no pagination
- `llm-probe-qd10-integration.md:23` — "Pagination contract drift" at API level only
- `llm-probe-qd4-performance.md:20,28` — Pagination/infinite-scroll as performance category, not UI exhaustiveness

### Verdict: WARN

Pagination and infinite scroll exhaustiveness is effectively not addressed. Runtime probes achieve only incidental page-1 coverage. LLM probes cover API-level pagination contract drift (QD10) and performance aspects (QD4), but no probe systematically tests pagination controls, page navigation, sort+page combinations, or infinite scroll behavior.

## C1.9.10 — Scan Depth Verification (Post-Scan Audit)

### What the checklist requires

> Sau khi scan hoàn tất, chạy audit ngược: đếm TOTAL_COMPONENTS (grep export function/class/defineComponent), đếm SCANNED_COMPONENTS (unique files trong issue-registry.json), tính coverage. Pass khi coverage ≥ 95% components trong scope.

### What the probes actually do

**Per-probe summary tracking** exists in individual probes:

| Probe | Summary metric |
|-------|---------------|
| `P-QD9-interactive-smoke` VERIFY | `pages_visited`, `cta_tested`, `cta_skipped_destructive`, `signals_emitted` in `summary.json` |
| `P-QD9-feature-checklist-smoke` A5 | `features_checked`, `features_broken` in `meta.json` |
| `P-QD1-deep-ui-traversal` ACT | `pages_visited`, `buttons`, `forms`, `links` in `catalog-ui-pages.json` |
| `P-QD5-ui-traversal-deep` B1 | `ROUTE_COUNT` from static route grep |

**What's missing:**

| Required mechanism | Exists? |
|-------------------|---------|
| Count total components in source | **NO** — no `grep -rE 'export (default \|)function\|export (default \|)class\|defineComponent\|@Component' src/ \| wc -l` anywhere |
| Count scanned components (unique files in results) | **NO** — `issue-registry.json` has issues but no deduplicated file list for component coverage |
| Compute coverage ratio | **NO** — no `COVERAGE = SCANNED / TOTAL * 100` calculation |
| Post-scan audit step in orchestrator | **NO** — `phase1-engine.md` and `post-gate-completion.md` have no "Step: Scan Depth Verification" |
| Cross-probe component coverage aggregation | **NO** — no mechanism to merge per-probe coverage into a global coverage metric |
| Coverage gate (< 85% → block) | **NO** — no gate or CDG point for insufficient coverage |

**Broader architecture note:**

The skill's architecture is signal-driven, not coverage-driven. The orchestrator dispatches probes, collects signals, aggregates, and fixes — but never asks "did we scan everything we should have?" The quality gates (CQG, Workload Gate, Safety Check) validate signal quality and fix correctness, not scan completeness.

**Evidence:**
- `P-QD9-interactive-smoke.md:339-361` — VERIFY: per-probe summary.json with pages_visited, cta_tested, but no component-level coverage
- `phase1-engine.md` — Full procedure: no "scan depth verification" step before or after Phase 3
- `post-gate-completion.md` — POST-GATE steps: fix-impact.json, orchestrator-summary.md, phase-summary.md — no coverage verification
- Grep for `TOTAL_COMPONENTS|SCANNED_COMPONENTS|coverage.*component` in procedures/ → **0 matches**

### Verdict: WARN

No post-scan depth verification mechanism exists. Probes track their own internal metrics (pages visited, features checked, CTAs tested) but there is no cross-probe aggregation, no total-vs-scanned component count, and no coverage ratio computation. The orchestrator has no step dedicated to verifying scan completeness.
