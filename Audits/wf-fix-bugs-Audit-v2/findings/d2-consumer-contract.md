## Findings

### D2-001 — Template by_dimension only QD1-QD8 (HIGH)

**Evidence:**
- `templates/fix-impact.json` L20-28: `by_dimension` only lists QD1 through QD8
- Template is authoritative source per CORE-031 (Template Usage Rule)
- `_contract.json` L63 references `templates/fix-impact.json` as template

**Expected:** by_dimension should cover QD1-QD11 (11 lanes in wf-fix-bugs v9.1.0)

**Actual:** QD9 (v8.2.0), QD10 (v9.0.2), QD11 (v9.1.0) missing from template

**Impact:** Consumers reading `by_dimension` field would not find QD9/QD10/QD11 entries. Template is the contract — when the template says 8 dimensions, downstream code may hardcode 8-dimension assumptions.

**Fix:** Add QD9, QD10, QD11 entries to `by_dimension` in template.

---

### D2-002 — Builder DIMENSIONS array missing QD11 (HIGH)

**Evidence:**
- `scripts/wf-fix-impact-builder.sh` L180-182:
  ```bash
  # CRIT-3 fix: loop QD1-QD10 thay vi hardcode QD1-QD8 (root cause v9.0.0 fantasy bug)
  # Khi them dimension moi (vd: QD11), chi can them vao DIMENSIONS array.
  DIMENSIONS=(QD1 QD2 QD3 QD4 QD5 QD6 QD7 QD8 QD9 QD10)
  ```

**Analysis:** The v9.0.0 fantasy completion bug was caused by hardcoding QD[1-8] everywhere. The CRIT-3 fix expanded the range to QD1-QD10 but the comment on L181 explicitly mentions QD11 should be added — yet it wasn't. This is the same bug pattern repeating itself: a dimension was added (QD11 in v9.1.0) but the DIMENSIONS array was not updated.

**Impact:** fix-impact.json generated by the builder WILL NOT include `by_dimension.QD11` statistics, even if QD11 issues exist in the session. The `by_dimension` field silently drops QD11 data.

**Fix:** Add QD11 to DIMENSIONS array: `DIMENSIONS=(QD1 QD2 QD3 QD4 QD5 QD6 QD7 QD8 QD9 QD10 QD11)`

**Note:** Root cause analysis — the comment says "Khi them dimension moi (vd: QD11), chi can them vao DIMENSIONS array" but this was never done. Suggests the v9.1.0 release checklist didn't include a "verify all DIMENSIONS arrays" step.

### D2-003 — Consumers don't check `.status` field for "degraded" (MEDIUM)

**Evidence:**
- `_contract.json` L63: "Downstream (wf-verify-sync, wf-prepare-deployment) MUST check .status field — 'degraded' → block consume"
- `wf-fix-impact-builder.sh` L29-31: "Downstream consumers (wf-verify-sync, wf-prepare-deployment) PHẢI check `.status` field — nếu 'degraded' → block consume + thông báo user manual review."
- `wf-verify-sync/procedures/phase0-init.md` L87 (Step 0.20): Only validates `$schema == "fix-impact-v1"` — no `.status` check
- `wf-prepare-deployment/procedures/phase1-prereq.md` L172: Only validates `$schema == "fix-impact-v1"` — no `.status` check
- `wf-implement-feature/procedures/phase1-feature-context.md` L63 (Step 1.10): Only validates `$schema == "fix-impact-v1"` — no `.status` check

**Analysis:** The builder writes `status: "degraded"` when it can't assemble a complete fix-impact.json (stub fallback — inputs missing, jq assembly failure, etc.). The contract explicitly requires consumers to check this field and block consumption. None of the 3 consumers implement this check.

**Impact:** If wf-fix-bugs POST-GATE fails to generate fix-impact.json (degraded stub), consumers would silently load incomplete data: missing `fix_summary`, empty `by_dimension`, no `audit_chain`, and `next_recommended_action.skill = "manual-review"`. The Go/No-Go gate in wf-prepare-deployment would pass because `escalated` defaults to 0 and `tests_failed` defaults to 0 in the degraded stub.

**Fix for wf-verify-sync (Step 0.20):**
```bash
# After $schema validation, add:
STATUS=$(jq -r '.status // "ok"' "$FROM_FIX_BUGS_SESSION_DIR/fix-impact.json")
if [ "$STATUS" = "degraded" ]; then
  REASON=$(jq -r '.degraded_reason // "unknown"' "$FROM_FIX_BUGS_SESSION_DIR/fix-impact.json")
  WARNING "fix-impact.json status=degraded: $REASON. Block consume — khuyến nghị manual review."
  set $FIX_IMPACT_CONTEXT = null; jump to POST-GATE
fi
```

**Fix for wf-prepare-deployment (Step 1.9):** Same pattern — after `$schema` validation, check `.status`, warn, set context to null, skip Go/No-Go gate.

### D2-004 — Template and builder generator version mismatch (LOW)

**Evidence:**
- Template: `"generator": "wf-fix-bugs v8.2.0"` (L56)
- Builder: `"generator": "wf-fix-bugs v7.4.0"` (L435)

**Impact:** Cosmetic — makes it harder to trace which version produced the file. Template version suggests v8.2.0 but builder writes v7.4.0.

**Fix:** Update builder L435 from `"wf-fix-bugs v7.4.0"` to `"wf-fix-bugs v9.1.0"` (or current version). Update template L56 to match.

## Observations

### OBS-D2-001 — All 3 consumers validate `$schema` correctly

All three consumers validate `jq -e '."$schema" == "fix-impact-v1"'` before parsing. Schema gate is consistent and correct. **PASS.**

### OBS-D2-002 — Auto-resolve logic identical across consumers

All three use the same pattern:
```bash
jq -r 'select(.status=="completed")|.session_id' _index/sessions.jsonl | sort | tail -1
```
Consistent across wf-verify-sync, wf-prepare-deployment, wf-implement-feature. Explicit session_id override via `=<id>` also identical. **PASS.**

### OBS-D2-003 — wf-implement-feature has dual consumption paths

Fix-impact.json is consumed through TWO independent paths:
1. **Phase 1 (Step 1.10-1.11):** `--from-fix-bugs` flag → feature prioritization by code_files overlap
2. **Phase 0-7 Safety Gate (Step 3.5):** DEFAULT behavior (no flag needed) → N=3 recent sessions conflict detection

Path 2 is more comprehensive (scans 3 sessions, proactive conflict detection). Path 1 is opt-in and single-session. Both load and parse fix-impact.json independently. No conflict between them. **PASS — architecture observation.**

### OBS-D2-004 — Go/No-Go gate asymmetry by design

wf-prepare-deployment has full Go/No-Go gate (escalated>0 BLOCK, tests_failed>0 BLOCK, audit_chain WARN). wf-verify-sync only cross-checks registry_changes but does NOT block execution — consistent with verify-sync's role as verification tool, not deployment gatekeeper. **PASS — by design.**

### OBS-D2-005 — wf-verify-sync also consumes docs-sync-report.json

In addition to fix-impact.json, wf-verify-sync also loads `docs-sync-report.json` (schema `docs-sync-report-v1`) from the same wf-fix-bugs session when `--from-fix-bugs` is passed. This is a secondary artifact not part of the fix-impact contract but correctly documented in phase0-init.md Step 0.21. **PASS.**

### OBS-D2-006 — post-gate-completion.md correctly references builder

`post-gate-completion.md` L213-221 correctly invokes `bash .claude/scripts/wf-fix-impact-builder.sh --session-dir "$SESSION_DIR"` and documents the required verify step (schema must be fix-impact-v1 + has key fields). Graceful degrade: builder exit != 0 → log WARN, không block POST-GATE. **PASS.**
